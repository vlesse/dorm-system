# 宿舍管理系统 · Dormitory Management System

面向**海外工业园区**的企业级员工宿舍管理系统。为印尼中苏拉威西 Morowali 青山工业园（IMIP）
的自建宿舍设计 —— 八栋楼、近三千张床位、上万名中方与印尼籍员工混住的真实场景。

> 一句话概括：**让宿舍数据变准，让日常运营有据可查。**

## 为什么会有这个项目

海外工业园区的宿舍管理有一组和国内学生宿舍完全不同的约束，市面上的开源宿舍系统
（多为课程设计）没有一个能用：

- **人数规模大且流动快** —— 上万人，入职、离职、休假、调岗天天发生
- **多国籍混住** —— 中方与印尼籍作息、饮食、语言、宗教都不同，分区不是可选项
- **合规压力实在** —— 消防疏散要求"此刻"的准确在住名单；护照 / KITAS 过期等于非法居留
- **数据一旦不准就全废** —— 人走了床位没释放，一个月后系统显示满床、实际空着几百张

这套系统就是围绕这些约束做的。

## 核心设计原则

这五条是整个系统的地基，改动代价最高，也最值得先理解：

**1. 最小可分配单位是「床位」，不是房间。**
上下铺各自独立；夫妻房的双人床按两个铺位建模，保持「一人一铺位」不变量。
把房间当最小单位的系统，三班倒排不了、事故追溯查不到、空床数永远不准。

**2. 入住是「带时间区间的记录」，永不覆盖。**
调宿 = 关掉旧记录 + 新建新记录，两条都留着。一张床的历史就是这张表的多行。
事故追溯、传染病密接排查、警方与劳工部检查，全靠这个。

**3. 三个「人数」是三件事，不能混。**

| | 含义 | 存在哪 |
|---|---|---|
| 标称规格 | 「四人间」就是 4 | `RoomType.defaultCapacity` |
| **核定人数** | 这间实际按几人住，可以是 3 | `Room.capacity` |
| 物理床位 | 屋里真有几张床 | `Bed` 表行数 |

「四人间实际住三人」是园区里的常态（空调制冷量不足、面积不够、主管批准降标）。
降标后多余的床标记为 `DISABLED` 并记录原因，不会再被排人进去，但仍留痕。

**4. 住宿的人不只有员工。** 还有家属随迁（配偶、子女）、长期访客、实习生、承包商工人。
消防名单、房间占用、门禁都要算上他们。

**5. 所有业务口径都在配置表里，不写死在代码。**
国籍、部门、职级（含休假周期）、班次、宗教、承包商、房型、17 条排宿规则的松紧，
全部在「设置」页改，改完立即生效，不用改代码、不用重启。

## 功能一览

<details open>
<summary><b>空间与排宿</b></summary>

- **五级空间模型**：园区 → 楼栋 → 楼层 → 房间 → 床位。国籍与性别策略**逐级继承**
  （房间 > 楼层 > 楼栋），支持「一二层印尼籍、三四层中方、五六层不限」这种楼层级混住
- **18 种房型**：13 种住人房（单/双/三/四/六/八人间、夫妻房、家庭房、干部单间、专家公寓、
  酒店式客房、隔离房、中转房）+ 5 种**功能房**（洗衣房 / 祷告室 / 活动室 / 宿管室 / 储藏室，
  占楼层空间但不住人）
- **楼层平面图**：走廊两侧排布，房间格子里画出真实床位小方块，哪张床空着一眼看到；
  可按入住率 / 国籍分区 / 房型三种口径着色。另有「楼栋剖面图」一屏看完全园区
- **床位图**：楼层从下往上排；房间网格；核定人数调整（降标）、加床、床位报修、房间资产与工单
- **17 条排宿规则引擎**，每条三档（关闭 / 仅提醒 / 强制拦截）：
  男女不同房、夫妻房须配偶关系、家属须与挂靠员工同房、房型职级门槛、**上下铺限制**、
  无障碍需求、国籍归属、同房同班次、同房同部门、自有与承包商不混住、
  **饮食禁忌一致**、吸烟习惯一致、**房内语言可沟通** 等
- 硬约束不通过 `400` 拦下；软约束不通过 `409` 带提醒返回，宿管确认后可继续。**硬约束 `force` 也越不过去**

</details>

<details open>
<summary><b>人员与家属</b></summary>

- 人员档案含国籍、证件（护照 / KTP / KITAS）与到期日、部门、职级、班次、雇佣主体、
  **宗教信仰**、语言、是否吸烟、**能否睡上铺**、**是否需要低楼层**、紧急联系人
- **夫妻与家属**：配偶 / 子女关系登记与核验，**整户一次安排夫妻房**，夫妻房占用总览
- **休假周期挂在职级上**（支持小数）：普通员工 6 个月、工程师/科长 5.5、部长/经理 4.5、总经理 3
- **密接排查**：某人某时间窗内的同房间 / 同楼层接触者 —— 时间区间模型天生支持

</details>

<details open>
<summary><b>日常运营</b></summary>

- **申请审批**：调宿 / 退宿 / 夫妻房 / 访客留宿 / 加床。审批与执行分离，责任清楚
- **报修工单**：类别各自的 SLA 时限、派工流转、**影响住宿的工单自动封房**并在完成后转待清洁、完成后员工评价
- **违规记录**：私拉电线 / 大功率电器 / 明火等分级扣分罚款、积分排行、超阈值告警
- **访客登记**：**留宿必须审批**，超期未离开告警
- **查寝与检查**：夜间查寝**自动生成该层在住人员点名清单**；卫生 / 安全检查按房打分记问题
- **物品与押金**：床上用品、钥匙、门禁卡的发放与归还，**退宿时强制清点**，未归还会拦住退宿并列出赔偿
- **公告**（三语，可按楼栋定向）

</details>

<details open>
<summary><b>报表与合规</b></summary>

- **在住花名册**：含家属；CSV 带 BOM，Excel 直接打开不乱码；字段含证件、宗教、紧急联系人
- **消防疏散清单**：按楼 → 层列出此刻在住的人，**需协助疏散的单独标出**，可直接打印
- **15 类待办告警** —— 都是「不主动查就发现不了、但迟早会出事」的地方：

  | | |
  |---|---|
  | 离职未退宿 | 数据失真头号原因，支持一键批量清退（含物品结算） |
  | 证件即将到期 | 护照 / KITAS 过期 = 非法居留 |
  | 报修超时未完成 | 按各类别自己的 SLA 算 |
  | 房间超住 | 在住人数超过核定人数 |
  | 夫妻房异常 | 单人独占夫妻房 / 已登记配偶却分住两处 |
  | 家属未与员工同房 | |
  | 休假即将到期 | 按各自职级周期推算 |
  | 违规积分超限 | |
  | 访客超期未离开 | |
  | 申请待审批堆积 | |
  | 物品未归还 | 人已退宿但物品没清 |
  | 已分配超期未入住 | |
  | 状态口径不一致 | 员工状态与床位状态脱节 |
  | 降标与床位不一致 | 降标了但床没撤 |
  | 功能房被占住 | |

</details>

<details open>
<summary><b>员工自助端（移动优先，三语）</b></summary>

访问 `/m`，与管理端完全隔离（独立 token、独立路由、独立样式）。

- **不发账号密码** —— 工号 + 手机验证码，或企业平台扫码
- **我的住宿**：房号铺位、房间设施、室友名单、下次休假、证件到期提醒
- **报修**：位置强制取自己住的房间，可看进度、修完评价
- **申请**：调宿 / 退宿 / 夫妻房 / 访客留宿 / 加床；同类型待审批只能有一条防重复刷；可撤销
- **我的**：通知、按楼栋定向的公告、领用物品与押金、违规积分
- **房门二维码**：管理端可为单间生成或整层批量打印，员工扫码直达该房间并一键报修
- 越权在入口一次堵死：员工 token 只能访问 `/api/self/*`，其余一律 403

</details>

<details open>
<summary><b>登录、权限与集成</b></summary>

- **两拨用户两种登录**：管理端账号密码（几十人）；员工走企业身份或手机验证码（上万人不发密码）
- **权限点** `模块:动作`，**楼栋数据范围**贯穿看板 / 花名册 / 疏散 / 全部告警 ——
  A 栋宿管和主管打开同一张看板，看到的数字不一样
- **审计日志**：分配、调宿、退宿、降标、改配置、登录失败全部留痕，操作人取自 token
- **15 个集成平台占位**（企业微信 / 钉钉 / 飞书 / Teams / 泛微 e-cology / 致远 A8 /
  用友金蝶 HR / 通用 OA / **海康威视** / **大华** / LDAP / 短信 / 邮件 / **WhatsApp** / 通用 Webhook），
  按 SSO / 人员同步 / 消息推送 / 审批流 / 视频接入 / 门禁联动六种能力建模，凭据由管理员自己填
- **通知中心**：业务代码只管「发生了什么」，不管发到哪个平台；按收件人国籍自动选中文 / Bahasa / 英文；
  一条事件扇出到多渠道，渠道未启用时记录原因而不是静默丢弃
- **人工批量导入**：人员 / 楼栋房间 / 入住分配三类，**Excel 模板带「填写说明」表页**，
  先预检（不写库、逐行给错因）后导入，有错的行可跳过

</details>

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Node.js ≥20 · TypeScript · Fastify 5 · Prisma 6 | 单进程，无外部依赖服务 |
| 数据库 | SQLite（默认）/ PostgreSQL | schema 按 PG 兼容写法书写，切换只需改 provider |
| 前端 | React 18 · Vite 6 · Ant Design 5 | 管理端 + 移动端自助端同一个 SPA |
| 认证 | 自实现 JWT（HMAC-SHA256）+ scrypt | 有意不引第三方库，逻辑短、行为可控 |
| 语言 | 中文 / Bahasa Indonesia / English | 界面与通知模板均三语 |

**为什么认证不用第三方库**：JWT 签验和密码哈希用 `node:crypto` 手写不到 80 行，
行为完全可控，也少一层供应链风险。见 [`server/src/services/auth.ts`](server/src/services/auth.ts)。

## 快速开始

前置：**Node.js ≥ 20**（推荐 22 LTS）、npm ≥ 10。

```bash
git clone https://github.com/vlesse/dorm-system.git
cd dorm-system

npm run setup     # 装依赖 + 生成 .env + 建库 + 灌模拟数据（首次约 2 分钟）
npm run dev       # 同时启动后端 3101 和前端 5183
```

打开 http://localhost:5183 ，用 `admin` / `dorm@2026` 登录。

生成的模拟数据规模：

```
8 栋楼 · 678 间房（含 66 间功能房、108 间降标房）
2999 张床位（其中 108 张按降标撤除）
2558 人（含 58 名家属随迁）· 80 对已核验配偶
193 条报修工单 · 130 条违规 · 45 条访客 · 24 次检查 · 31 条申请
```

重新生成数据：`npm run db:seed`（会先清空业务数据）。

## 路线图

已完成的见上面「功能一览」。**尚未实现**（照实列，不粉饰）：

- [ ] **企业平台的具体 adapter** —— 登录框架、身份绑定、通知渠道抽象、人员同步入口、
      15 个平台的凭据表单都已就绪，但各平台真实 API 调用需要企业凭据才能实现和联调
- [ ] **费用结算** —— 住宿费按人天、水电按在住人天分摊、承包商月结账单、工资扣款清单。
      单价字段（`RoomType.dailyRate`、`ItemType.price/deposit`）已经在存了
- [ ] **监控接入** —— `Device` 表已为摄像头预留点位；主应用不碰码流，
      二期起独立视频网关（go2rtc / MediaMTX）把 RTSP 转 WebRTC 即可
- [ ] **门禁联动** —— 入住即开权限，退宿即注销
- [ ] **移动端离线** —— 楼里信号差时先本地暂存再同步
- [ ] **房间平面坐标** —— 目前平面图按房号奇偶分列走廊两侧；真实楼型各异，
      理想做法是给房间加坐标字段让宿管拖一次排定
