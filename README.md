# 宿舍管理系统 · 青山园区（IMIP）

印尼中苏拉威西 Morowali 青山工业园自建宿舍的企业级管理系统。
目标是**让宿舍数据变准、让日常运营有据可查**：床位级建模、时间区间入住记录、
可配置的排宿规则、随时能交出去的在住花名册，以及报修、违规、访客、查寝、物品押金等日常运营闭环。

## 跑起来

```bash
npm run setup   # 安装依赖 + 建库 + 生成模拟数据（首次）
npm run dev     # 同时起后端 3101 和前端 5183
```

打开 http://localhost:5183

重新生成模拟数据：`npm run db:seed`（会先清空业务数据，配置字典也会重建）

## 五条不能动的设计原则

1. **最小可分配单位是床位（Bed），不是房间。** 上下铺各自独立；夫妻房的双人床按两个铺位建模，
   保持「一人一铺位」不变量。
2. **入住是带时间区间的记录（Occupancy），永不覆盖。** 调宿 = 关掉旧记录 + 新建新记录，两条都留着。
   事故追溯、密接排查、警方与劳工部检查全靠这个。
3. **三个「人数」是三件事，不能混：**
   - `RoomType.defaultCapacity` —— **标称规格**（"四人间"就是 4）
   - `Room.capacity` —— **核定人数**（这间实际按几人住，可以是 3）
   - `Bed` 的实际条数 —— **物理床位**（降标撤掉的床 `status=DISABLED`，仍留痕）
4. **住宿的人不只有员工**：还有家属随迁（配偶、子女）、长期访客、实习生、承包商工人。
   消防名单、房间占用、门禁都要算上他们。
5. **所有业务口径都在配置表里，不写死在代码。** 改完立即生效，不用改代码、不用重启。

## 数据模型

```
Site 园区
 └ Building 楼栋 (8 栋，层数不等；默认国籍 / 性别策略 / 有无电梯)
    └ Floor 楼层 (国籍归属可单独覆盖 —— 支持「1、2 层印尼籍，3 层中方」)
       └ Room 房间 (房型 / 核定人数 / 降标原因 / 状态机 / 设施)
          ├ Bed 床位  ← 真正的可分配资源
          └ Asset 房间资产 (空调 / 热水器 / 床架 / 桌椅)

Person 人员 ──< Occupancy 入住记录 (时间区间) >── Bed
Relationship 亲属关系 (SPOUSE / CHILD…，带「已核验」标记 —— 夫妻房的前置条件)
Request 申请审批  IssuedItem 物品发放  Deposit 押金
WorkOrder 报修工单  Violation 违规  Visitor 访客  Inspection 查寝检查
Announcement 公告  Device 设备（为二期监控预留）
Role / User / UserBuilding 角色与数据范围
```

空间策略**逐级继承**：房间 > 楼层 > 楼栋。留空表示跟随上级，上级也留空表示不限。

| **夫妻房** | 2 | 允许男女同住，**强制要求已核验的配偶关系** |
| **家庭房** | 4 | 夫妻 + 随迁子女 |

| 专家公寓 | 1 | 职级门槛 rank≥50（经理以上） |
| 酒店式客房 | 2 | `managementMode=HOTEL`，短住 / 可预订 / 按天计费 |
| 隔离 / 病号房 | 4 | 默认封锁，需要时开启 |
| 中转 / 临时房 | 6 | 新到未定岗、短期过渡 |
| 洗衣房 / 祷告室 (Mushola) / 活动室 / 宿管室 / 储藏室 | 0 | **功能房**，占楼层空间但不住人 |

### 「四人间实际住三人」怎么表达

在房间上把**核定人数**改成 3（床位图 → 点房号 → 调整核定人数），系统会：
- 把多出来的**空床**自动标记为 `DISABLED`（降标撤除），床位图上显示为灰色斜纹 ×，不会再被排人进去
- 记录**降标原因**（空调制冷量不足 / 面积偏小 / 床架损坏 / 主管批准…）
- 已经住人的床不会被动；如果在住人数已超过要设的核定人数，接口会拒绝并提示先调宿
- 「待办告警」会盯着**核定人数与可用床位对不上**的房间

## 排宿规则引擎

`server/src/services/rules.ts`。**17 条规则**，每条三档：`OFF 关闭` / `SOFT 仅提醒` / `HARD 强制拦截`。

| 规则 | 默认 | 为什么 |
|---|---|---|
| 房间须可用 | HARD | 维修 / 隔离 / 封锁的房间不能进人 |
| 功能房不得住人 | HARD | 洗衣房、祷告室不是宿舍 |
| 不得超过核定人数 | HARD | 按核定，不是按标称 |
| 床位须可用 | HARD | 降标撤除、报修中的床不能分 |
| 男女不同房 | HARD | 夫妻房 / 家庭房自动豁免 |
| **夫妻房须配偶关系** | HARD | 必须是已登记且已核验（结婚证）的配偶两人 |
| **家属随迁限制** | HARD | 家属只能住允许家属的房型，且必须与挂靠员工同房 |
| 房型职级门槛 | HARD | 干部单间、专家公寓 |
| **上下铺限制** | HARD | 标记「不能睡上铺」的人不分上铺 —— 这是安全问题 |
| 无障碍需求 | SOFT | 行动不便的人安排在三层以下，或有电梯的楼 |
| 国籍符合区域归属 | **SOFT** | 确实存在混住，不能一刀切拦死 |
| 同房同班次 | SOFT | 白班夜班混住是宿舍矛盾第一来源 |
| 同房同部门 | SOFT | 紧急集合、班车方便 |
| 自有与承包商不混住 | SOFT | 费用结算主体不同 |
| 饮食禁忌一致 | SOFT | 清真 / 非清真共用炊具易起矛盾 |
| 吸烟习惯一致 | SOFT | 既是矛盾来源也是火灾风险 |
| 房内语言可沟通 | SOFT | 紧急情况喊得动人 |

接口行为：硬约束不通过 → `400` 拦下；软约束不通过 → `409` 带提醒返回，
前端弹窗让宿管确认，确认后带 `force: true` 再提交。**硬约束 `force` 也越不过去。**

候选床位打分（`scoreAssignment`）由 seed 批量排宿和 API 推荐**共用同一套**，保证两边口径一致。

## 待办告警（15 类）

都是「不主动查就发现不了、但迟早会出事」的地方：

1. **离职未退宿** —— 数据失真头号原因，支持一键批量清退（含物品结算）
2. **证件即将到期** —— 护照 / KITAS 过期 = 非法居留
3. **报修超时未完成** —— 按各类别自己的 SLA 算
4. **房间超住** —— 在住人数超过核定人数
5. **夫妻房异常** —— 单人独占夫妻房 / 已登记配偶却分住两处
6. **家属未与员工同房**
7. **休假即将到期** —— 按各自职级周期推算
8. **违规积分超限** —— 累计扣分达阈值
9. **访客超期未离开**
10. **申请待审批堆积**
11. **物品未归还** —— 人已退宿但物品没清
12. **已分配超期未入住**
13. **状态口径不一致** —— 员工状态与床位状态脱节
14. **降标与床位不一致** —— 降标了但床没撤
15. **功能房被占住**

## 登录与权限

**两拨用户，两种登录方式** —— 给上万工人发账号密码在园区里是运维灾难，所以分开：

| | 人数 | 登录方式 |
|---|---|---|
| **管理端**（宿管 / 主管 / HR / EHS） | 几十人 | 账号密码，或企业平台扫码 |
| **员工本人** | 2500+ | **不发账号密码** —— 企业微信 / 钉钉扫码，或工号 + 手机验证码。绑定关系存在 `IdentityBinding`，`personId` 指向员工档案 |

技术上有意不引第三方库：JWT 用 `node:crypto` 的 HMAC-SHA256 手写，密码用 scrypt，
逻辑很短、行为可控，也少一层供应链风险。见 `server/src/services/auth.ts`。

### 演示账号（初始密码统一 `dorm@2026`，除 admin 外首登强制改密）

| 账号 | 角色 | 能看到什么 |
|---|---|---|
| `admin` | 系统管理员 | 全部，含集成凭据 |
| `dorm.chief` | 宿舍主管 | 全部楼栋、可改日常阈值，**改不了集成凭据** |
| `warden.a` … `warden.h` | 楼栋宿管 | **只看得到自己那栋楼** |
| `hr01` | 人力资源 | 人员为主 |
| `ehs01` | 安全环保 | 违规、检查、报表 |

### 权限点与数据范围

权限点写成 `模块:动作`，`*` 全部、`模块:*` 模块内全部。关键的几条划分：

- `space:read` 看空间 / `space:room` 改房间与床位状态（宿管可以）/ `space:write` 改国籍分区与楼栋属性（主管）
- `space:capacity` **改核定人数（降标）—— 主管以上**，因为降标是管理决定
- `config:write` 日常阈值与字典（主管）/ `integration:write` **集成平台凭据（仅管理员）**
- `space:all` 不受楼栋范围限制

**数据范围**通过 `UserBuilding` 限定到楼栋。同一个看板，不同角色看到的数字不一样：

```
A栋宿管    床位  650 | 在住人  466 | 工单  9 | 违规  8 | 告警 211
C栋宿管    床位  672 | 在住人  620 | 工单  8 | 违规 15 | 告警 232
宿舍主管   床位 2999 | 在住人 2432 | 工单 75 | 违规 41 | 告警 735
```

菜单也按权限过滤 —— 没权限的项直接不显示，而不是点进去报 403。

### 审计

有了登录，「谁干的」才是真的。分配、调宿、退宿、降标、改配置、改集成、登录失败
全部落 `AuditLog`，操作人取自 token 而不是前端传的字符串。

## 集成对接

**对接不是一件事，是四件**，价值和难度差很远：

| 能力 | 是什么 | 价值 | 难度 |
|---|---|---|---|
| `SYNC` 人员同步 | 花名册单一来源，离职自动触发退宿 | **最高** | 中 |
| `NOTIFY` 消息推送 | 工单、审批、证件到期推到手机 | 高 | **最低** |
| `SSO` 扫码登录 | 员工不用记一套密码 | 高 | 中 |
| `APPROVAL` 审批流 | 走公司现有 OA 审批 | 中 | **最高**，建议缓做 |

已登记的平台（`设置 → 集成对接`，凭据由管理员填，secret 字段只以打码形式返回）：

能力除了前面四种，还加了 `VIDEO` 视频接入和 `ACCESS` 门禁联动。**共 15 个平台**，
每个平台需要填哪些凭据字段都已列清，管理员自己填、自己启用：

| 平台 | 能力 | 备注 |
|---|---|---|
| 企业微信 | SSO / SYNC / NOTIFY / APPROVAL | 中方员工主用 |
| 钉钉 | 同上 | 与企业微信二选一 |
| 飞书 / Lark | 同上 | 同类，看总部用哪个 |
| **WhatsApp Business** | NOTIFY | **印尼籍员工的主要触达渠道** —— 他们不用企业微信 / 钉钉 |
| Microsoft Teams / Entra ID | SSO / SYNC / NOTIFY | 有欧美合资方时才需要 |
| 公司 OA / HR 接口（通用 HTTP） | SYNC / APPROVAL | 自研 / 其他 OA 走这个 |
| **泛微 e-cology** | SYNC / APPROVAL | 国内中大型企业常见 OA |
| **致远 A8 OA** | SYNC / APPROVAL | 与泛微二选一 |
| **用友 / 金蝶 HR** | SYNC | 花名册在 HR 系统而不在 OA 里时走这个 |
| **海康威视 综合安防平台** | VIDEO / ACCESS / SYNC | 楼道监控 + 门禁 |
| **大华 DSS 平台** | VIDEO / ACCESS | 与海康同类 |
| LDAP / AD 域 | SSO / SYNC | 园区已有域控时可用 |
| 短信网关 | NOTIFY | 兜底：不装 App 的工人也能收到 |
| 邮件 SMTP | NOTIFY | 管理层日报 / 周报 |
| **通用 Webhook** | NOTIFY | 任何自研 / 第三方系统，POST JSON 即可接收事件 |

### 通知中心

**业务代码只管「发生了什么」，不管发到哪个平台。** 触发点调 `notify(templateCode, target, vars)`，
通知中心负责：查模板 → 按收件人语言渲染（中方中文 / 印尼籍 Bahasa / 其余英文）→
按模板配置的渠道逐个落一条发件记录 → 站内信直接就绪，外部渠道交给 adapter。

一条业务事件的实际效果：

```
主管批准一条申请
  → IN_APP    SENT     你的申请已批准
  → WECOM     SKIPPED  WECOM 渠道未启用（设置 → 集成对接）
  → WHATSAPP  SKIPPED  WHATSAPP 渠道未启用（设置 → 集成对接）
```

发件箱里一眼能看出哪些消息因为平台没配置而没发出去。接入具体平台时，
只需实现 `ChannelAdapter.send()`，业务代码一行不用改（`server/src/services/notify.ts`，
每个占位里写清楚了接进来需要哪些参数）。

内置 13 个三语模板：床位分配、调宿完成、报修派工 / 完成、申请批准 / 驳回、
违规记录、证件到期、离职退宿待办、公告推送、查寝未归、**自助端登录验证码**、**员工提交申请**。

### 人员同步

接口 `POST /api/sync/persons`，Excel 导入和企微 / 钉钉 / OA / LDAP 拉取走**同一个入口**。
关键行为：**外部把某人标记为离职时，系统自动生成一条已批准的退宿待办并推送给对应楼栋宿管** ——
这才是「离职未退宿」的根治点，不用等宿管自己发现。

## 员工自助端

地址 `/m`，移动优先，和管理端**完全隔离**：独立 token（`dorm.selfToken`）、独立路由、独立样式。
宿管和员工可以在同一台设备上分别登录，互不影响。

### 登录：不发账号密码

工号 + 手机验证码。验证码通过短信 / WhatsApp 渠道下发；这两个渠道都还没启用时，
后端会**把验证码直接回显并说明原因**，所以平台接入之前系统照样能用、能演示，
状态是明说的，不会让人以为是 bug。企业平台扫码（企业微信 / 钉钉 / 飞书）的入口和
绑定关系（`IdentityBinding.personId`）已经就绪，凭据配好即可启用。

演示工号：`CN00001` / `CN00002` / `ID00003`

| **我的住宿** | 楼栋 / 楼层 / 房号 / 铺位、房间设施、入住日期、**室友名单**、下次休假、证件到期提醒 |
| **报修** | 选类别 → 一句话描述 → 提交。位置强制取自己当前住的房间，不能乱报别人房间。可看进度、完成后评价 |
| **申请** | 调宿 / 退宿 / 夫妻房 / 访客留宿 / 加床。同类型待审批的只能有一条，防重复刷；可撤销 |
| **我的** | 通知、公告（按楼栋定向）、领用物品与押金、违规记录与积分 |

**夫妻房申请有前置校验**：没有已核验的配偶关系、或职级未开放，提交时直接挡下并告诉他该去哪办。

### 越权是从入口堵死的

员工 token 的 `kind = 'PERSON'`，权限固定只有 `self`。全局钩子里一条规则：
**PERSON token 只能访问 `/api/self/*`，其余一律 403** —— 不依赖每个路由自己记得加守卫。
所有自助端查询强制以 token 里的 `personId` 为准，不接受前端传 id。

实测：

```
员工 token → /api/dashboard    403
             /api/persons      403
             /api/alerts       403
             /api/roster       403
             /api/integrations 403
             /api/audit-logs   403
             /api/self/profile 200
```

### 房门二维码

床位图 → 点房号 → **门牌二维码**，或楼层工具栏 → **打印门牌**（整层批量，可直接打印）。
员工扫码进 `/m/room/{房号}`，看到房间信息并一键报修。二维码里的地址取自
「设置 → 阈值 → 自助端基址」，**上线前记得填成园区内网地址**。

二维码贴在门上谁都能扫，所以扫码页只显示房间的公开信息（房型、设施、在办工单数），
**不列住户名单**，只告诉你「是不是你住的房间」。

## 人工批量导入

菜单「系统 → 批量导入」。和「集成对接 → 人员同步」是两条腿：系统还没对接、或者对接不上时，
拿 Excel / CSV 也能把数据灌进来，两边最后都落到同一张同步日志。

**流程：下载模板 → 填数据 → 上传 → 预检 → 确认导入。**

| 导入类型 | 干什么 | 需要权限 |
|---|---|---|
| **人员花名册** | 导入员工与家属。工号已存在则更新。**标记为「已离职」且仍占床位的，自动生成退宿待办并通知宿管** | `person:write` |
| **楼栋房间** | 批量建楼建房。楼栋 / 楼层不存在自动创建；**新建房间按房型自动摆好床位**（上下铺、双人床都按规格），核定人数小于标称时多余床位自动标记降标撤除 | `space:write` |
| **入住分配** | 批量把人安排进房间。床位留空则自动挑一张空床。**导入时跑一遍排宿规则**：硬约束不通过的行直接判错，软约束不通过只提醒 | `allocation:write` |

几个刻意的设计：

- **字段定义只有一份**（`server/src/routes/imports.ts` 的 `TYPES`）。模板表头、页面上的字段说明、
  后端校验读的都是它，不会出现「模板里有这列、导入却说不认识」。
- **Excel 模板带两个表页**：`数据`（表头 + 示例行）和 `填写说明`（每个字段的必填与否、
  可选值全列出来）。填表的人不用来回问「部门能填哪些」。
- **预检不写库**，逐行返回是新增还是更新、哪行有问题、问题是什么。有错的行可以跳过，
  不必整批重来。
- 字典按中文名匹配（「电厂」「工程师」「白班」），不用让人去背 ID。
- 导入全程留审计日志，操作人取自登录身份。

## 监控接入（二期，架构已预留）

一期**不接码流**，但点位已经登记在 `Device` 表里（每层楼一个楼道摄像头，`isActive: false`）。

二期只做两件事：
1. 起一个独立的视频网关容器（[go2rtc](https://github.com/AlexxIT/go2rtc) 或 MediaMTX），
   把海康 / 大华的 RTSP 转成浏览器直接能播的 WebRTC；
2. 在「设置 → 设备点位」把 `streamPath` 填上、`isActive` 打开。

**主应用永远不碰视频码流**，只管两件事：这层楼有哪些摄像头、当前用户有没有权限看。
所以接监控不用动主库、不用改数据模型。

部署上要注意：系统应装在**园区内网服务器**（监控流不能出园区，园区外网也不稳），外部访问走 VPN。
