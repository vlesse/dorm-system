## 空间管理

### 五级模型

```
园区 Site
└── 楼栋 Building        A ~ H，8 栋，层数各不相同（4 / 6 / 8 层）
    └── 楼层 Floor
        └── 房间 Room     含住人房与功能房
            └── 床位 Bed  最小可分配单位
```

**为什么最小单位是床位不是房间。** 三个理由，每一个单独拿出来都够：

1. 上下铺是两个独立的位置。有人怕高、有人腰椎不好、有人年纪大 —— 「这人必须睡下铺」
   是一条要落到具体位置上的约束，房间级别表达不了。
2. 事故追溯要精确到铺位。火灾、盗窃、打架，需要知道**当时谁睡在哪张床**。
3. 空床数得准。只记「四人间住了 3 人」，就不知道空的是哪张、是不是上铺、能不能排给新人。

### 国籍与性别策略的逐级继承

现实场景是这样的：A 栋整栋印尼籍，B 栋一二层印尼籍、三四层中方、五六层不限，
C 栋整栋中方但某几间留给外籍专家。

系统的做法是**房间 > 楼层 > 楼栋逐级覆盖，留空即继承上级**：

- 楼栋设 `nationalityId = ID`（印尼籍）
- 三层单独设 `nationalityId = CN` → 该层所有房间跟着变中方
- 某间房单独设 `nationalityId = null` → 不限国籍

界面上会显式标出「继承自 B 栋」还是「本层单独设定」，改的时候不会误以为改的是全楼。
性别策略（男 / 女 / 夫妻 / 不限）走同一套继承。

### 房型与功能房

18 种房型，分两类：

**住人房（13 种）**：单人间、双人间、三人间、四人间、六人间、八人间、夫妻房、家庭房、
干部单间、专家公寓、酒店式客房、隔离 / 观察房、中转 / 临时房

**功能房（5 种）**：洗衣房、祷告室（Mushola，穆斯林员工的实际需求）、活动室、宿管室、储藏室

功能房**占楼层空间但不排人**。很多系统不建模功能房，结果楼层平面图上是个洞，
入住率算不准，也没法回答「这层楼到底有多少间房」。功能房被违规住人会进告警。

### 三个「人数」

这是本系统最容易被误解、也最重要的一处建模。

| | 字段 | 含义 |
|---|---|---|
| **标称规格** | `RoomType.defaultCapacity` | 「四人间」这个房型的名义人数 = 4 |
| **核定人数** | `Room.capacity` | **这一间实际按几人住**，可以是 3 |
| **物理床位** | `Bed` 表行数 | 屋里真有几张床 |

「四人间实际住三人」在园区里非常普遍，原因五花八门：空调制冷量不够、人均面积不达标、
主管特批、房间朝向差。这不是数据错误，是**降标（de-rating）**，是一个需要被记录、
被审批、被追溯的业务动作。

系统的处理：调低 `Room.capacity` 时必须填降标原因，多出来的床位自动置为
`status = DISABLED` —— 不再参与分配，也不算进空床数，但**床还在表里**，
将来恢复标准配置时改回来即可，历史入住记录也不会因为床没了而断掉。

**空床数 = 核定人数 − 当前在住**，永远不用物理床位数去算。

### 平面图与剖面图

- **楼层平面图**：走廊两侧排布房间（按房号奇偶分列），每个房间格子里画出真实床位小方块，
  空床、住人、停用一眼分清。三种着色口径可切换：入住率 / 国籍分区 / 房型。
- **楼栋剖面图**：八栋楼并排，楼层从下往上堆叠，一屏看完整个园区的松紧。

两者在总览页可互相切换。

## 人员与家属

### 档案字段

除了常规的姓名、工号、部门、职级，还存了一批**直接影响排宿的字段**：

| 字段 | 为什么要 |
|---|---|
| 国籍 | 分区的依据 |
| 证件类型与号码、到期日 | 护照 / KTP / KITAS。**过期 = 非法居留**，会进告警 |
| 班次 | 白班和夜班同房，两边都睡不好 |
| 雇佣主体 | 自有员工与承包商工人不混住（合规与管理责任划分） |
| 宗教信仰 | 影响饮食禁忌与作息（斋月），也影响祷告室的排布 |
| 语言 | 一间房里没有共同语言，出事没法互相求助 |
| 是否吸烟 | 混住是宿舍矛盾第一名 |
| 能否睡上铺 | 年龄、腰椎、恐高 |
| 是否需要低楼层 | 行动不便、心脏病 |
| 紧急联系人 | 出事第一时间要找的人 |

### 住宿的人不只有员工

系统里的 `Person` 覆盖五类：**正式员工、家属随迁（配偶 / 子女）、长期访客、实习生、承包商工人**。

消防疏散名单、房间占用统计、门禁权限都必须把这些人算进去。
只管员工的系统，火灾的时候会漏掉一屋子的家属。

### 夫妻与家属关系

- 登记 `Relationship`（配偶 / 子女 / 父母），**需要核验**（`verified`）才能用于夫妻房
- **整户一次安排**：选中一对已核验的配偶，一次性分配到同一间夫妻房的两个铺位
- 夫妻房占用总览：谁和谁住在哪
- 告警会盯住两种异常：**单人独占夫妻房**（浪费稀缺资源）、**已登记配偶却分住两处**

### 休假周期挂在职级上

不同职级的休假周期不同，这是海外派驻的常态：

| 职级 | 周期（月） |
|---|---|
| 普通员工 | 6 |
| 工程师 / 科长 | 5.5 |
| 部长 / 经理 | 4.5 |
| 总经理 | 3 |

周期是 `PositionLevel` 上的一个字段（支持小数），在「设置 → 职级」里随时改，不写死在代码里。
告警会按各自的周期推算「休假即将到期」。

### 密接排查

给定一个人和一个时间窗，查出这段时间内和他**同房间 / 同楼层**住过的所有人。

这个功能之所以能存在，完全是因为入住记录是带时间区间的（见下一节）。
如果入住表被覆盖式更新，历史就没了，这个查询根本写不出来。

## 床位分配

### 入住是「带时间区间的记录」

`Occupancy` 表的每一行是 `(人, 床, 入住时间, 退宿时间, 状态)`。**永远不覆盖、不删除**。

- **入住** = 新建一条 `checkOutAt = null` 的记录
- **调宿** = 关掉旧记录（填上 `checkOutAt`）+ 新建一条新记录
- **退宿** = 关掉记录

一张床的历史，就是这张表里 `bedId` 相同的多行按时间排列。
一个人的住宿履历，就是 `personId` 相同的多行。

这个决定是后面一堆功能的地基：事故追溯、密接排查、住宿费按人天结算、
劳工部检查时「三个月前这张床住的谁」。

### 分配流程

1. 选人 → 系统给出**推荐床位列表**，按打分排序，每个候选标出会触发哪些规则提醒
2. 选床 → 实时校验（`GET /api/allocation/check`）
3. 确认 → 硬约束不通过直接拦下；软约束不通过弹出提醒，宿管确认后可继续
4. 写入 `Occupancy` + `OccupancyEvent` + `AuditLog`

**操作人取自登录 token，不是前端传上来的字符串** —— 「谁把人排进去的」这个问题必须有确定答案。

### 候选打分

`scoreAssignment()` 是**推荐列表和批量排宿共用**的同一个函数，保证两边口径一致：

```ts
let score = 100 - 触发的提醒条数 * 10;
if (房间国籍 === 本人国籍)              score += 25;
if (房型有职级门槛 && 本人达标)          score += 50;   // 干部单间优先给够级别的
if (本人职级 >= 40 && 房间核定 >= 4)     score -= 45;   // 经理以上不塞大房间
if (20 <= 本人职级 < 40 && 核定 >= 6)   score -= 12;
if (夫妻房)  score += 有已核验配偶 ? 60 : -100;
if (房间已有人)                         score += 8;     // 优先填满而不是开新房
if (下铺 && 本人不能睡上铺)              score += 15;
if (上铺 && 本人不能睡上铺)              score -= 100;
if (本人需要低楼层)                      score += max(0, 20 - 楼层 * 4);
```

### 其他分配动作

- **预留**（`reserveOnly`）：床位占住但人还没到
- **挂起 / 恢复**（`hold` / `resume`）：休假回国期间，床位保留但不算在住
- **夫妻房整户分配**（`couple`）：一次两个铺位
- **加床**：临时增加物理床位，需填原因

## 排宿规则引擎

17 条规则，每条三档：**关闭 / 仅提醒 / 强制拦截**，在「设置 → 排宿规则」里逐条调。

| 规则 code | 名称 | 默认档 | 说明 |
|---|---|---|---|
| `roomStatus` | 房间须可用 | 强制 | 维修 / 隔离 / 封锁 / 待清洁的房间不能进人 |
| `residential` | 功能房不得住人 | 强制 | 洗衣房、祷告室这类房占空间但不住人 |
| `capacity` | 不得超过核定人数 | 强制 | **按核定人数算，不是房型标称** |
| `bedUsable` | 床位须可用 | 强制 | 降标撤除、报修中的床不能分配 |
| `gender` | 男女不同房 | 强制 | 夫妻房 / 家庭房自动豁免 |
| `couple` | 夫妻房须配偶关系 | 强制 | 必须是已登记**且已核验**的配偶两人 |
| `dependent` | 家属随迁限制 | 强制 | 只能住允许家属的房型，且必须与挂靠员工同房 |
| `positionRank` | 房型职级门槛 | 强制 | 干部单间、专家公寓有门槛 |
| `bunk` | 上下铺限制 | 强制 | 标记「不能睡上铺」的人不分上铺 —— 这是安全问题 |
| `accessibility` | 无障碍需求 | 提醒 | 行动不便的人优先低楼层 |
| `nationality` | 国籍归属 | 提醒 | **默认软约束 —— 确实存在同楼混住** |
| `shift` | 同房同班次 | 提醒 | 白班夜班混住两边都睡不好 |
| `department` | 同房同部门 | 提醒 | 便于管理和通知 |
| `contractor` | 自有与承包商不混住 | 提醒 | 合规与管理责任划分 |
| `religion` | 饮食禁忌一致 | 提醒 | 清真 / 素食 |
| `smoking` | 吸烟习惯一致 | 提醒 | 宿舍矛盾第一名 |
| `language` | 房内语言可沟通 | 提醒 | 一间房没有共同语言，出事没法互相求助 |

档位可以随时调 —— 比如国籍默认是「提醒」，某个园区要求严格分区，
就在设置里把 `nationality` 改成「强制」。

**强制档 `force` 参数也越不过去** —— 这是有意的。能被绕过的硬约束不是硬约束。
真要放宽某条，去设置里把它降成「仅提醒」，这个动作会留在审计日志里。

规则配置存在 `SettingItem` 表里，改完立即生效，不用重启。

## 日常运营

### 申请审批

五种申请：**调宿 / 退宿 / 夫妻房 / 访客留宿 / 加床**。

审批和执行是分开的两步：审批只表示「同意」，实际排床还要宿管去操作。
这样责任清楚 —— 批的人和做的人可以不是一个人，出问题各查各的。

员工端提交的申请，**同类型同时只能有一条待审批**，防止刷屏。可撤销。

### 报修工单

- 分类别，**每个类别有自己的 SLA 时限**（水电急、家具可以慢）
- 派工 → 处理中 → 完成 → 员工评价
- **影响住宿的工单会自动封房**（房间置为维修中，不再排人），完成后转「待清洁」
- 超过 SLA 未完成进告警

### 违规记录

私拉电线、大功率电器、明火、留宿外人、损坏公物等，分级扣分 + 罚款。
积分排行榜，超过阈值触发告警（阈值在设置里改）。

### 访客登记

来访登记、离开登记。**留宿必须走审批**。超期未离开进告警。

### 查寝与检查

- **夜间查寝**：选定楼层，系统**自动拉出该层此刻的在住人员名单**作为点名清单，
  逐个标记在 / 不在 / 请假。不用手抄名单，也不会漏人。
- **卫生 / 安全检查**：按房间打分、记录问题项，可关联生成整改工单。

### 物品与押金

床上用品、钥匙、门禁卡的发放与归还，各自带押金和单价。

**退宿时强制清点**：有未归还物品会**拦住退宿**，并列出赔偿清单。
这一条能挡掉大部分「人走了东西不知去向」。

### 公告

三语，可按楼栋定向发布，员工端可见。

## 报表与合规

### 在住花名册

含家属。可按楼栋、楼层、国籍、部门、雇佣主体筛。

**CSV 导出带 UTF-8 BOM** —— Excel 直接双击打开不乱码。这个细节很小，但少了它，
每次导出都要手动改编码，宿管会直接放弃用这个功能。

导出字段含证件类型与号码、宗教、紧急联系人 —— 应付检查的时候要的就是这些。

### 消防疏散清单

按楼 → 层列出**此刻**在住的所有人（含家属和访客），
**需要协助疏散的人单独标出**（行动不便、孕妇、老人）。可直接打印。

演习和真实事故的时候，这张表就是清点依据。

## 待办告警

15 类。共同点是：**不主动查就发现不了，但迟早会出事**。

| 告警 | 为什么重要 |
|---|---|
| **离职未退宿** | 数据失真头号原因。支持一键批量清退（含物品结算） |
| **证件即将到期** | 护照 / KITAS 过期 = 非法居留，会被罚 |
| 报修超时未完成 | 按各类别自己的 SLA 判定 |
| 房间超住 | 在住人数 > 核定人数 |
| 夫妻房异常 | 单人独占 / 配偶分住两处 |
| 家属未与员工同房 | |
| 休假即将到期 | 按各自职级周期推算 |
| 违规积分超限 | |
| 访客超期未离开 | |
| 申请待审批堆积 | |
| 物品未归还 | 人已退宿但物品没清 |
| 已分配超期未入住 | 床占着没人住 |
| 状态口径不一致 | 员工状态与床位状态脱节 |
| 降标与床位不一致 | 降标了但床没撤 |
| 功能房被占住 | |

告警**受楼栋数据范围约束** —— A 栋宿管只看到 A 栋的待办。

## 员工自助端

访问 `/m`。移动优先，与管理端完全隔离：独立 token（`dorm.selfToken`）、独立路由、独立样式。

### 不发账号密码

上万名员工，发密码这件事本身就是灾难 —— 忘记、泄露、重置，宿管会被淹没。

所以员工端只有两条登录路径：

1. **企业平台扫码**（企业微信 / 钉钉 / 飞书，凭据配好后自动出现）
2. **工号 + 手机验证码**

短信 / WhatsApp 渠道没启用时，后端会**直接回显验证码**并标记 `devFallback`，
方便演示和内网试用。真接了渠道之后这个回显自动消失。

### 功能

| | |
|---|---|
| **我的住宿** | 房号铺位、房间设施、室友名单、下次休假、证件到期提醒 |
| **报修** | 位置强制取自己住的房间（不用输，也不会填错），看进度，修完评价 |
| **申请** | 调宿 / 退宿 / 夫妻房 / 访客留宿 / 加床，可撤销 |
| **我的** | 通知、公告（按楼栋定向）、领用物品与押金、违规积分 |

### 房门二维码

管理端可为单间生成，或**整层批量打印**。员工扫码直达该房间页面，一键报修。

二维码里的地址取自请求的 `Origin`（回落 Referer / Host），
也可以在「设置 → 自助端」里用 `self.baseUrl` 强制指定 —— 反代场景下需要。

### 三语

中文 / Bahasa Indonesia / English。**按本人国籍自动选**：中国籍 → 中文，
印尼籍 → Bahasa，其他 → English。也可手动切。

字典项（房型、部门、职级、班次）由后端返回 `{zh, id, en}` 三元组，
不是前端硬编码 —— 新增一个部门不用改前端。

## 权限与数据范围

### 两拨用户，两种登录

| | 管理端 | 员工端 |
|---|---|---|
| 人数 | 几十 | 上万 |
| 登录 | 账号 + 密码 | 工号 + 验证码 / 企业扫码 |
| token 种类 | `USER` | `PERSON` |
| 可访问 | 全部 `/api/*` | 只有 `/api/self/*` |

**越权在入口一次堵死**：`server/src/index.ts` 的全局 `onRequest` 钩子里，
`PERSON` token 访问任何非 `/api/self/` 路径一律 403。
不依赖每个路由自己记得加守卫 —— 那种设计迟早会漏。

### 权限点

`模块:动作` 形式，支持 `*`（全部）和 `模块:*`（该模块全部）。
例：`space:read`、`allocation:write`、`config:*`、`integration:write`。

### 楼栋数据范围

`UserBuilding` 表把用户和楼栋关联起来。**这个范围贯穿看板、花名册、疏散清单、全部告警**。

A 栋宿管和宿舍主管打开同一张看板，看到的数字不一样 —— 这不是 bug，是设计。
演示环境用 `warden.a` 和 `admin` 对比登录就能直观看到。

### 审计日志

分配、调宿、退宿、降标、改配置、登录失败全部留痕。
**操作人取自 token**，不是前端传的字符串。

## 平台对接与通知

### 15 个平台占位

| 类别 | 平台 |
|---|---|
| 国内协同 | 企业微信、钉钉、飞书 |
| 国际协同 | Microsoft Teams |
| OA / 审批 | 泛微 e-cology、致远 A8、通用 OA |
| HR | 用友、金蝶 |
| 安防 | **海康威视 iSecure**、**大华 DSS** |
| 目录 | LDAP / AD |
| 消息 | 短信网关、邮件 SMTP、**WhatsApp Business** |
| 通用 | Webhook |

按六种能力建模：**SSO 单点登录 / 人员同步 / 消息推送 / 审批流 / 视频接入 / 门禁联动**。
每个平台定义了自己需要的凭据字段（corpId、agentId、appSecret……），管理员在界面上填。
**读取时密钥字段自动打码**。

**目前这些是完整的框架 + 占位实现**：登录入口、身份绑定、通知渠道抽象、
人员同步入口、凭据表单、连通性测试按钮都在，但各平台真实 API 调用需要企业凭据才能实现和联调。
接一个平台需要写的，就是一个实现 `ChannelAdapter` 接口的文件（见 [开发文档](DEVELOPMENT.md#接一个新的通知渠道)）。

### 通知中心

业务代码只管**发生了什么**，不管发到哪里：

```ts
await notify('WORKORDER_ASSIGNED', { personId: 123 }, { orderNo, title });
```

剩下的由通知中心处理：
- 按模板 code 找到模板
- **按收件人国籍挑语言**（CN → 中文，ID → Bahasa，其他 → English）
- 渲染变量
- 扇出到所有启用的渠道（站内信 + 企业微信 + WhatsApp……）
- **渠道没启用时记录原因，而不是静默丢弃** —— 这样排查「为什么没收到通知」有据可查

站内信永远可用，不依赖任何外部平台。

## 批量导入

三类数据可人工批量导入：

| 类型 | 需要权限 | 用途 |
|---|---|---|
| **人员** | `person:write` | 新员工花名册 |
| **楼栋房间** | `space:write` | 新楼投用 |
| **入住分配** | `allocation:write` | 已有住宿关系补录 |

### 流程

1. **下载模板** —— CSV 或 Excel。**Excel 模板带第二个「填写说明」表页**，
   逐字段说明必填与否、取值范围、示例。
2. 填好上传，前端解析。
3. **预检** —— 不写库，逐行返回 `新增 / 更新 / 错误`，错误行给出具体原因，
   还会给出警告（不阻塞但值得看一眼）。
4. **导入** —— 可选「跳过有错的行」。

**入住分配的导入会跑完整的排宿规则引擎** —— 硬约束不通过的行会被标错，
不会因为走了导入通道就绕过校验。

模板表头、界面字段说明、后端校验规则**共用同一份定义**
（`server/src/routes/imports.ts` 的 `TYPES` 数组），三者永远不会对不上。

## 系统设置

**所有业务口径都在这里改，不写死在代码里。** 这是第五条设计原则的落地。

| 配置项 | 内容 |
|---|---|
| 国籍 | 代码、中/印/英名称、默认语言 |
| 部门 | |
| 职级 | 名称、**排序权重（rank）**、**休假周期月数** |
| 班次 | 名称、起止时间 |
| 宗教 | 名称、饮食禁忌 |
| 雇佣主体 | 自有 / 各承包商 |
| 房型 | 名称、标称人数、**职级门槛**、日单价、是否功能房 |
| 物品类型 | 名称、单价、押金 |
| 工单类别 | 名称、**SLA 小时数**、是否影响住宿 |
| 违规类型 | 名称、扣分、罚款 |
| **排宿规则** | 17 条，各自的关闭 / 提醒 / 强制 |
| 阈值 | 证件到期提前天数、休假提前天数、违规积分上限、未入住超期天数…… |
| 自助端 | 二维码基地址、验证码有效期 |

改完立即生效，不需要改代码，不需要重启。

**职级的 rank 是数字不是枚举**，因为「够不够级别住干部单间」这种判断需要可比较的序，
而现实中职级体系会变（加一级副经理），枚举扛不住。
